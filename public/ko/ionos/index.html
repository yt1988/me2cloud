직접 연결 규칙: 깨끗한 측정을 위해

테스트용 도메인만 프록시를 거치지 않고 직접 연결하면, 프록시가 아닌 내 회선을 측정할 수 있어요. 규칙은 테스트용 도메인에만 적용되고 다른 트래픽은 그대로예요.

    작동 원리와 자주 묻는 질문

    핑 사이트나 Looking Glass보다 내 네트워크에서 재는 게 정확한 이유

    결론부터: 나에게 빠른지 알려면 내 네트워크에서 재야 해요.

    대부분의 '클라우드 핑' 사이트와 업체의 Looking Glass는 그들의 서버에서 측정해요. 데이터센터 안, 좋은 회선에 물린 서버라서 알 수 있는 건 '데이터센터에서 데이터센터까지'의 속도뿐이에요. 내가 실제로 느끼는 부분, 즉 집이나 모바일 회선, 통신사 백본, 해외로 나가는 구간, 오늘 밤 얼마나 붐비는지는 잴 수 없어요.

    Me2Cloud는 모든 요청을 내 브라우저에서 보내요. 그래서 Wi-Fi, 공유기, 통신사, 통신사가 고르는 경로, 저녁 피크까지 모두 결과에 들어가요.

    핑 사이트 / Looking GlassPC에서 ICMP pingMe2Cloud
    어디서 측정하나그들의 데이터센터내 네트워크내 네트워크
    통신사와 저녁 피크 반영안 됨됨됨
    웹·앱과 같은 프로토콜(TCP 443)경우에 따라아님, ICMP맞음, HTTPS
    네트워크가 속도 제한·차단하나가끔자주드묾
    리전 수백 곳을 한 번에일부안 됨됨
    설치 필요없음없음없음

    측정은 이렇게 해요

    1. 먼저 워밍업 요청을 한 번 보내 DNS 조회, TCP 연결, TLS 암호화를 마쳐요. 이 시간은 보여 주지만 결과에는 넣지 않아요.
    2. 그다음 같은 연결로 같은 호스트에 5회, 10회, 또는 20회 요청을 더 보내요. 한 번에 드는 건 왕복 1번과 업체 서버의 짧은 처리 시간뿐이에요.
    3. 업체마다 연결이 유지되는 걸 확인한 요청 방식을 써요. AWS, Azure, Google Cloud, DigitalOcean, Scaleway는 GET, Oracle, IBM Cloud, Alibaba Cloud, Tencent Cloud, Volcengine, Baidu AI Cloud, Naver Cloud, Huawei Cloud, Linode, Vultr, OVHcloud, IONOS Cloud, Aruba Cloud, Leaseweb, Gcore, Yandex Cloud는 HEAD(GET을 받으면 연결을 끊어서 값이 약 3배가 되기 때문), Hetzner는 CORS 모드의 GET이에요(그렇지 않으면 브라우저가 응답 페이지를 중간에 자르고 연결도 끊겨요).
    4. 결과에는 중앙값(가장 전형적인 값), 평균, P90(10번 중 9번은 이 값 이하), 지터(연속된 두 측정값의 평균 차이), 타임아웃 비율(제한 시간 안에 응답이 없던 비율)이 나와요.
    5. 등급은 중앙값으로 정해요: T0 갓 ≤ 30 ms, T1 최상급 ≤ 80 ms, T2 상위권 ≤ 150 ms, T3 NPC ≤ 250 ms, 그보다 크면 T4 망함. '추천 리전'은 '중앙값 + 2 × 지터 + 타임아웃 감점' 순으로 정렬해서, 안정적인 60 ms가 들쭉날쭉한 45 ms보다 앞에 와요.

    HTTPS로 재는 게 ICMP ping보다 실제 체감에 가까운 이유

    • 평소 트래픽과 같은 길로 가요. 웹사이트, API, 443 포트 터널, 게임 로그인, 다운로드는 모두 TCP를 써요. ICMP만 따로 줄 세우거나 속도를 줄이거나 다른 경로로 보내는 통신사가 많아서, 핑은 좋은데 페이지는 느리거나 그 반대인 경우가 흔해요.
    • 속도 제한에 묻히지 않아요. 공유기와 클라우드는 ICMP를 제한하거나 버리는 일이 잦지만, 공개된 HTTPS 지점은 항상 응답해요.
    • 실제 환경이 그대로 들어가요. DNS, IPv4·IPv6 선택, 프록시, 가속기는 모두 브라우저 트래픽에 적용돼요. 그래서 실제로 얻을 속도를 재게 돼요.
    • 대신: 측정값마다 아주 안정적인 서버 처리 시간이 조금 들어가요. 실측으로 AWS는 0–5 ms, Alibaba Cloud는 약 8 ms, Huawei Cloud OBS는 약 20 ms였어요. 100 ms가 넘는다면 신경 쓸 필요 없고, 아주 가까운 리전은 ping보다 약간 높게 나와요.

    언제 잴까: 저녁 피크 시간을 노리세요

    • 가정용 회선은 저녁 20:00–23:00쯤 가장 붐비고, 해외로 나가는 구간은 더 심해요. 낮에 T1이던 리전이 밤에는 NPC까지 떨어지기도 해요.
    • 낮에 한 번, 저녁 피크에 한 번 재 보세요. 피크 때 결과에는 '저녁 피크' 표시가 붙고, 결과 화면에서 바꿔 가며 비교할 수 있어요.
    • 측정하는 동안 큰 다운로드, 동영상, 클라우드 동기화는 멈추세요. 유선이 Wi-Fi보다 정확하고, Wi-Fi라면 공유기 가까이에서 재세요.
    • 모바일 데이터는 신호 세기에 따라 결과가 달라져요. 실제로 쓸 장소에서 재세요.

    이럴 때 쓰면 좋아요

    • 서버, 게임 서버, CDN 오리진을 계약하기 전에 후보 리전을 추리기.
    • 한 업체의 리전끼리, 또는 같은 도시의 업체끼리 비교하기.
    • 지터와 타임아웃 비율이 게임, 화상 회의, 원격 데스크톱, SSH에 충분한지 확인하기.
    • 프록시, 가속기, 새로 바꾼 인터넷이 정말 좋은지, 켜고 한 번, 끄고 한 번 재서 확인하기.
    • 직접 추가한 측정 지점으로 내 서버나 CDN을 대형 업체와 나란히 비교하기.

    알 수 없는 것

    • 한 위치의 값만 나와요. 내 회선을 재는 것이지, 내 사용자의 회선이 아니에요. 사용자 몇 명에게 측정을 부탁하고, 내보내서 비교하세요.
    • 업체의 공개 지점을 재는 것이지, 앞으로 쓸 서버 자체가 아니에요. 각 리전의 공개 API나 스토리지 주소를 재요. 같은 리전의 서버는 보통 같은 네트워크를 쓰지만, 프리미엄 경로(예: CN2, BGP와 단일 통신사, Lightsail과 EC2)는 다를 수 있어요.
    • 대역폭, UDP, 경로 추적은 재지 않아요. 왕복 시간만 재기 때문에 다운로드 속도, UDP 게임 트래픽, 중간 경유지는 알 수 없어요. 다운로드 속도는 속도 테스트로 재세요.
    • 브라우저 탓에 오차가 생겨요. 확장 프로그램, 프록시, VPN, 무거운 탭은 결과를 흔들어요. 무거운 탭은 닫고 이 페이지를 앞에 띄워 두세요.
    • 일부 측정 지점은 몇몇 나라에서 연결되지 않을 수 있어요.

    개인정보: 테스트는 브라우저에서 보내고, 결과는 업로드하지 않아요

    • 결과는 업로드하지 않고, 가입도 필요 없어요. '결과 공유'를 누를 때만, 채팅 앱에서 보여 줄 수 있도록 결과를 짧은 링크와 미리보기 이미지로 1ms.dog에 저장해요.
    • 테스트 요청은 모두 브라우저에서 업체로 바로 가요. 위의 요청 기록이나 브라우저 개발자 도구의 Network 탭에서 하나하나 볼 수 있어요.
    • 네트워크 정보는 Cloudflare에서 받아요. 먼저 이 사이트의 /_ms/me가 답하고, 최종적으로는 테스트와 같은 경로로 가는 speed.cloudflare.com/meta와 /cdn-cgi/trace의 값을 써요. 선택 사항인 WebRTC 확인은 stun.cloudflare.com에 UDP 출구 주소를 물어봐요. 원하지 않으면 설정에서 끌 수 있어요.
    • IPv4/IPv6 확인 때는 Cloudflare 밖의 ipify.org와 ident.me에도 물어봐요. 그중 하나가 네트워크에서 막혀도 IPv6가 없다고 잘못 판단하지 않기 위해서예요.
    • 페이지에 오류가 나면, 고치기 위해 오류 내용, 페이지 주소, 브라우저 버전을 이 사이트로 보내요. 공유 기능을 쓰면 어떤 단계를 썼는지 익명으로 집계해요. 어느 쪽에도 측정 결과는 들어가지 않아요.
    • 설정, 직접 추가한 측정 지점, 최근 결과는 이 브라우저 안에만 저장돼요. '측정 데이터 지우기'를 길게 누르면 결과와 기록이 지워지고, 설정까지 지우려면 브라우저에서 이 사이트의 데이터를 삭제하세요.

    업체에 부담을 주지 않아요: 속도 제한도 차단도 없어요

    공개 지점에 요청을 너무 세게 보내면 업체의 속도 제한이나 방화벽(WAF)에 걸리고, 결과도 틀어져요. 그래서 테스트 속도를 일부러 낮게 잡았어요:

    • 호스트마다 한 번에 요청 1개만 보내고, 측정 사이에 250–370 ms를 쉬어요(호스트당 초당 최대 2–3개).
    • 업체당 동시에 최대 2개 호스트, 전체로도 최대 8개(기본 4개).
    • 테스트 한 번에 호스트당 최대 21개 요청(워밍업 1개 + 최대 20개). 계속 보내는 모드는 없어요.
    • 3번 연속 실패한 호스트는 계속 재시도하지 않고 넘어가요.
    • 요청은 모두 익명이에요. 쿠키도 리퍼러도 보내지 않고, 사전 요청(preflight)도 없어요. 응답은 수백 바이트이고, 가능한 곳에서는 HEAD를 쓰며, 큰 파일은 내려받지 않아요.

    테스트 전체의 트래픽은 평범한 웹페이지 하나를 여는 것보다 적어요. 모든 측정 지점이 익명 요청에 정상 응답하는지 확인했어요(200, 403, 404 모두 측정에는 문제없어요).

    프록시나 VPN을 쓰고 있다면?

    트래픽이 프록시를 거치면, 브라우저가 재는 건 '나 → 프록시'와 '프록시 → 업체'를 더한 시간이지 내 회선이 아니에요. 네트워크 표시에서는 흔한 신호를 확인해요: 출구가 데이터센터 네트워크, 시간대와 출구 국가가 다름, WARP 켜짐, WebRTC와 HTTPS의 출구가 다름.

    직접 연결 규칙 받기로 테스트용 도메인만 직접 연결하게 한 뒤(Clash / Mihomo, Surge, Shadowrocket, Quantumult X, Loon, sing-box, Xray, SwitchyOmega, 도메인 목록 지원) 다시 확인하세요. 프록시 자체를 재고 싶다면 켠 채로 재세요. 그게 프록시의 실제 성능이에요.

    그래프 읽는 법

    • 모든 줄의 막대는 같은 눈금(로그 눈금, 2 ms~3 s)을 써요. 점은 측정값 하나하나, 음영 상자는 가운데 절반의 범위, 세로선은 중앙값이에요.
    • 상자가 좁을수록 안정적이에요. 상자가 넓거나 점이 흩어져 있으면 흔들림(지터)이 크다는 뜻이에요. 빨간 ×는 타임아웃된 횟수예요.
    • 줄을 누르면 측정값의 순서별 변화, 모든 통계, 사용한 측정 지점을 볼 수 있어요. ✓는 조건에 맞는 리전이에요.

    서버에서도 측정해 보세요

    VPS, Linux 서버, 공유기에서 이 명령을 실행하면 같은 리전을 거기서 측정할 수 있어요. 기본은 TCP 핸드셰이크로 재고(ICMP도 가능), 1분 정도면 끝나며, 마지막에 이 페이지에서 열 수 있는 결과 링크를 보여 줘요.

    AI 어시스턴트와 함께 쓰기

    AI가 내 회선을 대신 측정할 수는 없지만, 결과를 읽고 테스트를 준비하는 건 도와줄 수 있어요.

    요청 기록

    아래 요청은 모두 이 브라우저가 표시된 호스트로 직접 보낸 거예요. 결과는 업로드하지 않고, '결과 공유'를 누를 때만 결과를 짧은 링크로 저장해요. 브라우저 개발자 도구의 Network 탭에서 직접 확인할 수 있어요.
