直连规则：让测试结果更干净

把测试用的域名设成直连，测出来的才是你自己的线路，而不是代理的。规则只匹配测试域名，不影响其他流量。

    原理与常见问题

    为什么从你自己的网络测，比测速网站和 Looking Glass 更靠谱

    大部分“云节点测速”网站，以及厂商自己的 Looking Glass，测试都是从他们的服务器发起的。这些服务器放在机房里，接的是优质线路，测出来的只是“机房到机房”有多快。而你真正感受到的那一段，家里宽带或手机网络、运营商骨干、国际出口，还有今晚堵不堵，它们统统测不到。

    Me2Cloud 的每个请求都从你的浏览器发出，所以结果把这些全算进去了：Wi‑Fi、路由器、运营商、运营商选的路由，还有晚高峰。

    每次采样是怎么测的

    1. 先发一次预热请求，把 DNS、TCP、TLS 都建好。这次的时间会显示出来，但不计入结果。
    2. 然后在同一条连接上，对同一个主机再发 5、10 或 20 次请求。每次只花一个往返，再加上厂商服务器的处理时间。
    3. 每家厂商都用我们实测过、能保持连接的请求方式：AWS、Azure、Google Cloud、华为云、DigitalOcean、Scaleway 用 GET；Oracle、IBM Cloud、阿里云、腾讯云、火山引擎、百度智能云、Naver Cloud、Linode、Vultr、OVHcloud 用 HEAD（它们的 GET 会断开连接，测出来会翻 3 倍）；只有 Hetzner 用 <img>。
    4. 结果给出中位数（最典型的值）、平均值、P90（10 次里有 9 次不超过它）、抖动（相邻两次的平均变化）和丢包（超时没响应的次数）。
    5. 等级按中位数划分：T0 夯 ≤ 30 ms、T1 顶级 ≤ 80 ms、T2 人上人 ≤ 150 ms、T3 NPC ≤ 250 ms，再往上就是 T4 拉完了。推荐用的综合分是“中位数 + 2 × 抖动 + 丢包惩罚”，所以稳定的 60 ms 会排在忽高忽低的 45 ms 前面。

    为什么 HTTPS 测速比 ICMP ping 更贴近真实体验

    • 跟你的流量走同一条路。网页、API、走 443 的隧道、游戏登录、下载，用的都是 TCP。不少运营商对 ICMP 单独排队、限速，甚至单独选路，所以经常 ping 看着挺好、网页却卡得要死，反过来也有。
    • 不会被限速吞掉。路由器和云厂商经常限制甚至直接丢弃 ICMP，而访问公共 HTTPS 端点总会有响应。
    • 算上你的真实环境。DNS、IPv4/IPv6 的选择、代理、加速器，对浏览器流量都会生效，测出来的就是你实际能拿到的效果。
    • 代价是：每次采样还包含一点很稳定的服务器处理时间。我们实测 AWS 是 0–5 ms，阿里云约 8 ms，华为云 OBS 约 20 ms。延迟上百毫秒的节点完全可以忽略；离你特别近的区域，数字会比 ping 略高一点。

    什么时候测：专挑晚高峰

    • 家庭宽带在晚上 20:00–23:00 最堵，出国线路更明显。中午还是 T1 顶级的区域，到了晚上可能直接掉到 NPC。
    • 建议白天测一次、晚高峰再测一次。保存的结果会打上“晚高峰”标签，在测试结果里可以来回切换对比。
    • 测试时先暂停大文件下载、视频和网盘同步。有线比 Wi‑Fi 准；只能用 Wi‑Fi 的话，尽量离路由器近一点。
    • 用手机流量测，结果会跟着信号走。最好在你真正要用的地方测。

    适合用来干什么

    • 买服务器、游戏服、CDN 回源之前，先把候选区域筛一遍。
    • 比较同一家厂商的不同区域，或者同一个城市不同厂商的表现。
    • 看稳定性（抖动、丢包）够不够打游戏、开视频会议、远程桌面和 SSH。
    • 验证你的代理、加速器或者新办的宽带到底行不行：开着测一次，关掉再测一次。
    • 用自定义节点，把你自己的服务器或 CDN 跟大厂放在一起比。

    它做不到的事

    • 只代表一个位置。测的是你的线路，不是你用户的。可以让几个用户也测一下，导出来对比。
    • 测的是端点，不是你以后的云主机。我们测的是厂商在该区域的公共 API 或存储端点。同区域的服务器一般共用网络，但精品线路（比如 CN2、BGP 和单线、Lightsail 和 EC2）可能不一样。
    • 不测带宽、不测 UDP、不做路由追踪。只测往返时间，不测下载速度、UDP 游戏流量，也看不到中间经过哪些节点。
    • 浏览器本身的影响。插件、代理、VPN、很忙的标签页都会带来噪声。测试时关掉占资源的标签页，让本页保持在前台。
    • Hetzner 在浏览器里没法保持连接，所以它的数字每次都包含握手时间。个别端点在某些国家和地区可能访问不到。

    所有请求都从你的浏览器发出

    • 本页是放在 Cloudflare 上的纯静态文件。没有后端、不用注册、没有统计代码，结果也从不上传。
    • 所有测试请求都由你的浏览器直接发给厂商。打开上面的请求记录，或者浏览器开发者工具的 Network 面板，每一条都看得到。
    • 网络信息来自 Cloudflare（speed.cloudflare.com/meta 和 /cdn-cgi/trace）。可选的 WebRTC 检测会向 stun.cloudflare.com 询问你的 UDP 出口地址，不想用可以在设置里关掉。
    • IPv4/IPv6 检测会同时询问 Cloudflare 以外的 ipify.org 和 ident.me，某一家被网络阻断时，不会被误判成没有 IPv6。
    • 设置、自定义节点和最近几次结果只存在这个浏览器的本地存储里，“清空全部数据”会把它们全删掉。

    对厂商友好：不触发限流，也不会被封

    对公共端点请求太猛，可能触发厂商的限流或 WAF，结果也就不准了。所以测试节奏刻意压得很低：

    • 每个主机同一时间只有一个请求，两次采样之间停 250–370 ms（每个主机每秒最多 2–3 个请求）。
    • 每家厂商最多同时测 2 个主机，总共最多 8 个（默认 4 个）。
    • 每次测试每个主机最多 21 个请求（预热 + 20 次），没有持续轰炸的模式。
    • 连续失败 3 次就放弃这个主机，不会反复重试。
    • 全部是匿名、不带 Cookie、不带 Referer 的“简单请求”：没有预检，响应只有几百字节，能用 HEAD 就用 HEAD，不会下载大文件。

    整个过程的流量比打开一个普通网页还少。每个端点都验证过能正常响应匿名请求（返回 200、403、404 都不影响计时）。

    开着代理或 VPN 怎么办？

    流量走代理的话，浏览器测到的是“你到代理”加上“代理到厂商”，而不是你自己的线路。网络面板会检查几个常见迹象：出口网络属于机房、时区和出口国家对不上、开了 WARP、WebRTC 出口和 HTTPS 出口不一致。

    点获取直连规则，只把测试域名设成直连（支持 Clash / Mihomo、Surge、Shadowrocket、Quantumult X、Loon、sing-box、Xray、SwitchyOmega 和纯域名列表），然后重新检测。如果你想测的正是代理本身，那就开着测，得到的就是代理的真实表现。

    怎么看图

    • 每一行的条形图都用同一把尺子（对数刻度，2 ms 到 3 s）。圆点是每次采样，阴影框是中间一半采样所在的范围，竖线是中位数。
    • 框越窄越稳；框很宽或者点很散，就是抖得厉害。红色 × 是丢包的次数。
    • 点开一行，能看到每次采样的先后变化、全部统计数据和用到的端点。✓ 表示符合你的需求。
